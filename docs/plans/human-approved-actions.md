# Human-approved agent execution repair

## Goal and approved design
The user explicitly approved preserving approval for consequential actions while fixing every place where "you decide" became "you execute or edit the authorization file". Restore the existing finish-branch contract: prepare exact action, obtain actual human approval in the main conversation or host permission UI, have the agent execute through the normal tool, independently verify the result. Keep approval separate from its audit record.

Base: `0b98d833efa91c91ebeb2366ac69b1f62fd2f172` (`0b98d83`). Bash and PowerShell twins; no new dependency, credential store, approval token, shell runner, or automatic approval. No application merge, publish, commit, push, or downstream installation is authorized by this repair request.

## Root cause and smallest approach
The mutation hook unconditionally rejects recognized command text, including an approved merge, rather than consulting an approval mechanism. It cannot see the human conversation. Its pending-action helper renders only manual instructions and has no runner. PR and review-breaker prose conflates the person who decides with the person who writes the record. The existing V5-shaped runtime PR guard already permits agent transcription after the user says yes.

Retain the registered hook paths. In the interactive main session, emit no allow decision and defer to normal host permissions. Add native Claude ask rules in both settings templates for every previously blocked real command family (issue close, Kubernetes apply/delete/patch, curl mutation verbs), alongside the existing merge/PR/publish/deletion rules. These ask rules replace the removed denial; do not claim prose alone preserves the existing host prompt boundary. For unattended full investigators, the dispatcher sets FORGE_INVESTIGATION_CHILD=1 in the child process environment, and the hook continues to reject recognized consequential commands with an instruction to return the proposed action to the main session for human approval and agent execution. This marker restricts a child; it never authorizes anything. Handle this check before the ordinary isolated-review no-op. Explicit human authorization remains a main-session procedural boundary, as it already is for mutable PR/adjudication records; never claim a repository file authenticates the user. Do not invent an agent-set environment flag or file as permission. Existing Claude ask rules for merge/PR/publish/deletion and Codex host controls are preserved. Native host qualification remains separate; tests check generated ask-rule coverage, never claim they authenticate a chat reply. Ordinary isolated reviewers retain their existing sandbox/tool restrictions. A native host denial remains blocked; manual action is only a fallback when the actual tool is unavailable, not a blanket Forge rule.

The alternative of adding a custom approval-token authority would add a new subsystem and cannot authenticate a chat reply from repository code. It is unnecessary for the requested V5 behavior and is rejected.

## User journey acceptance
Actor: developer using Forge in Claude Code or Codex. Scenario: checks pass and a merge (or supported external mutation) is ready. Intent: decide whether to proceed without operating a terminal. Interface: conversation and existing host permission UI. Setup: exact target/candidate and clean required evidence. Steps: agent presents operation; user approves or declines; agent records actual approval, then uses the normal tool only when authorized. Verification: inert registered hook calls no longer demand terminal execution or emit automatic allow, host ask controls are preserved, reports do not claim success before independent readback. Persistence: current nonce/HEAD binding and stale authorization checks still apply. Live host UI interaction is a separate unverified boundary; deterministic tests cannot prove provenance of human input.
